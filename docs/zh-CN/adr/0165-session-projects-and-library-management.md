# ADR 0165：会话项目与会话库管理

[English](../../en/adr/0165-session-projects-and-library-management.md) · **简体中文**

- 状态：已接受
- 日期：2026-09-21
- 范围：可选项目分组、会话/项目增删改查，以及 TUI 管理界面

## 背景
会话恢复能力已经存在，但持久化存储只暴露"列出最近会话""恢复""重命名当前会话"。
用户无法主动新建会话、删除会话、重命名任意会话，也无法把相关工作分组。主流编码智能体
普遍允许一个项目拥有多个会话，而本项目此前完全没有这个概念。

设计受两条约束影响：

- 会话不能被强制归属项目——不属于任何项目的会话必须完全可用，且既有数据行必须继续工作；
- 会话生命周期已有唯一所有者（`ProfileConversationController`），它串行化回合、替换绑定
  并持有回合锁。会话管理不能成为第二个所有者。

## 决策
**项目是由会话存储拥有的可选分组。**
`SessionProject`（id、name、cwd、创建/更新时间）是 `neuro_code.domain.sessions` 中的
领域值对象；`normalize_project_name()` 负责规范化与长度上限，存储层保证规范化名称唯一。
`sessions` 表新增可空的 `project_id` 列，会话库 schema 推进到 v35，幂等创建
`session_projects` 表、名称唯一索引以及 `sessions(project_id, updated_at DESC, id DESC)`
索引。项目列被追加到既有会话投影末尾，因此不选取该列的窄投影继续可用。

删除项目只解除会话归属，绝不删除会话。项目消失后会话仍可寻址、恢复和搜索；`project_id`
无法解析的会话仍会列出，界面将其显示为属于已删除的项目。

**`SessionLibraryService` 拥有有界管理词汇。**
`neuro_code.application.sessions.library` 在既有 `SessionStore` 端口之上暴露项目增删改查、
任意会话重命名、会话删除与项目归属，并通过 `SessionLibraryOwner` 接缝暴露两项需要会话
所有者的操作：列出工作区会话与开启全新会话。该服务不做任何缓存。

**新建会话复用绑定替换路径。**
`ProfileConversationController.start_new_session()` 为当前配置构建全新绑定，断言其不带
会话 ID，应用既有会话策略，并在持有回合锁的情况下替换绑定。因此新会话与冷启动会话一样
惰性持久化：在首个回合写入，而原会话保持持久。没有引入新的存储路径，也不会急切创建
空会话。

**删除当前打开的会话会被拒绝。**
会话库抛出配置错误，而不是卸载已绑定的会话。删除会话会连带删除其事件，若对用户正在查看
的会话静默执行，就会丢弃当前对话。

**TUI 管理界面只负责呈现。**
`SessionLibraryScreen` 在两个可切换视图中呈现会话与项目，并返回一个类型化的
`SessionLibraryAction`；控制器经会话库服务执行后再重新打开该屏幕。行内显示所属项目，
操作包含打开、新建会话、重命名、移动到项目、删除，以及项目的创建、重命名、删除和
"查看会话"。破坏性操作需要显式确认模态，`/sessions` 打开管理器，`/resume` 保持直接恢复
行为。

## 后果
- 未归属项目的会话与 v35 之前创建的数据库继续可用；迁移按既有 v1→v35 链串行执行。
- 会话库服务与 TUI 屏幕由存储层、应用层和 Textual harness 测试覆盖；仅注入选择服务的
  嵌入方仍可使用原选择屏幕。
- 项目身份仅存在于会话库本地。导出/导入快照暂不携带项目归属，因此导入的会话以未归属
  状态出现。
- 权限、沙箱、验证与监督边界均无变化：项目归属只是展示与组织用的元数据。
